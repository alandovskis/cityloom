# Projects Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A project is a named container tied to one metropolitan area (Montreal only); everything a user edits is saved inside one, and the home page lists the user's projects.

**Architecture:** Every slice already reaches persistence through the `Storage` port, so a `ScopedStorage` decorator gives a page project-scoped copies of the per-project keys (`cityloom-edits`, `cityloom-restrictions`, `cityloom-area` and their `-damaged` copies) with no change to the stores. The sync is account-wide and works on the root storage: its wire keys carry the project (`<project>:<key>`), except the project `first`, whose keys stay bare, so every existing server row is already in the first project and the server needs no data migration. The project record is a new sync kind, `project`.

**Tech Stack:** Rust, Leptos 0.8 (wasm), Fluent `.ftl`, sqlx/Postgres, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-11-projects-design.md`

## Global Constraints

- Test-first; commit each task separately once tests pass; `just format` before committing; `RUSTFLAGS=-D warnings` (no new warnings).
- Dependency rule: `shared` depends on no slice; `sync::model` depends only on `shared`; a slice uses another's `model`, never its `vm`, views or text. The new `project/` slice may use `shared`, `sync::hub`/`sync::model`, `city::store` and `place::area`.
- Every new string is in `i18n/en.ftl` and `i18n/fr.ftl` with the same id and variables; whole sentences, plurals by selector; fr-CA per OQLF (`docs/glossary-fr-ca.md`). Wording goes through `Said`/`I18n`; register new files in `i18n_guard.rs` `MIGRATED`.
- WCAG 2.2 AA: a new colour pair goes in `shared/contrast.rs`; the list page has an `h1`/`h2` structure, skip link and focus order like the other pages.
- Project id format: 1–16 characters of `[a-z0-9-]`. The first project's id is exactly `first`. Ids of projects the user creates are `p-` plus 12 hex digits from `Storage::random_hex`, or `p1`, `p2`, … where storage has none (tests).
- Wire key: `<project>:<key>` for every project except `first`, whose key is bare. A bare key is therefore the first project's. Rule ids (`r-…`, `r<n>`), place keys (`n…`, `w…`) and `current` never start with `p-`, so the prefix is unambiguous. The `project` kind's key is the project id itself (`first` included); keys stay at most 200 characters; AAD scheme `work.<kind>.<key>.<user_id>` is unchanged.
- Montreal is the only area: a new project's area is `place::area::default_area()`.
- Every pull request raises the product version (minor: feature) in `crates/cityloom_editor/Cargo.toml` and runs `cargo update -p cityloom_editor`.
- Sharing, other areas, moving a project to another area: not built.

## Review Focus

Failure modes the spec implies; each has a test in the task named.

1. A prefixed key longer than 200 characters would be refused by the server: it must stay local and unlisted, never lost or sent (Task 3).
2. Two devices migrate the same legacy data independently: after syncing there is one `first` project (Task 4).
3. Legacy keys still present after migration, or projects already existing: the migration never runs twice and never overwrites (Task 4).
4. A page opened for a project id that does not exist (bad link, deleted elsewhere): the user lands on the list with a notice, never in a blank editor (Task 5).
5. A damaged or newer-version projects document: not read, not written, copied aside only when the user next changes the list; the edits of its projects stay reachable by id (Task 2).
